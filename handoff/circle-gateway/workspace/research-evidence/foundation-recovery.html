Category: Middleware / HTTP integrations

The gap between #277 and #1062

Issue #1062 covers the facilitator timeout race condition. Issue 277 covers the "already settled" query path. Between them is a state neither handles cleanly today. The facilitator has timed out and returned failure. The client received a definitive error and stopped. The transaction may still confirm on-chain without polling.

Scenario Covered by
Facilitator returns success; later queried as "already settled" 277
Facilitator times out; client retries with same nonce #1062
Facilitator times out; client receives failure; chain confirms during the silence This issue

Why this matters in practice

The Coinbase-hosted facilitator was calibrated around Solana-style expectations, where block times are often around 400ms. On Base under congestion, block inclusion can take much longer. Add client-side latency on a 3G connection, and the facilitator timeout can fire before the chain responds. The USDC may already have moved. The client has a failure response. Nobody is watching.

For applications in low-connectivity environments, this is not an edge case. It appears in remittance bridges, cross-border payment routing, marketplace split payments, and parametric settlement engines, all based on the same x402 settlement primitive. The failure cost is high because manual recovery is slow and working capital consequences are real.

Researchers at NDSS 2026 formalised this as the Two-Phase Gap. Their core observation is that x402 splits payment processing into a verify phase and a settle phase to keep latency low. That split creates a window where the same payment can be delivered twice or not at all, depending on what fails in between.

Proposed middleware

When the facilitator times out, the server should not immediately return a 402. Instead, middleware can move the settlement into an unresolved state, start polling Base directly, and hold resource delivery until the chain resolves the outcome.

States

State Trigger Server action
pending Transaction submitted to mempool Hold resource delivery
confirmed Facilitator confirms within timeout Deliver resource
unresolved Facilitator times out Begin direct chain polling
polling Active chain queries underway Hold resource delivery
confirmed_late Chain confirms during polling window Deliver resource
failed Transaction reverted on-chain Return definitive 402
failed_orphaned Polling exhausted, transaction not found Return definitive 402, flag for review

The on-chain EIP-3009 nonce provides permanent idempotency without requiring a database. The in-memory state only manages temporary delivery decisions. The EIP-3009 validBefore timestamp also gives a natural expiry boundary. If polling outlasts the authorisation window, the state can be discarded cleanly.

Environment profiles

Profile Facilitator timeout Initial poll interval Max poll window
datacenter 5s 2s 30s
east_africa_3g 15s 5s 90s
west_africa_3g 15s 5s 90s

Mobile money bridge variant

For applications bridging mobile money rails to x402 settlement, the middleware can accept a bridge-level idempotency key linking the mobile money transaction ID to the x402 nonce. This lets the bridge reconstruct the settlement state after a connectivity drop by querying either system independently.

Why this belongs at the middleware layer

Three clocks govern a settlement. They cannot be synchronised at the protocol layer because their values depend on deployment context the protocol cannot know.

Clock Domain Determined by
Protocol time Block inclusion and confirmation depth Base network conditions, gas competition
Application time HTTP timeout and response deadline Client requirements, server resource limits
Network time Round-trip latency, packet loss Physical infrastructure, ISP quality, geography

Pushing recovery policy into the protocol gives one universal policy that fits no deployment especially well. The state machine does not change what x402 guarantees on-chain. It changes how applications wait for and respond to those guarantees when the three clocks fall out of sync.

Current implementation status

I have built two supporting reference repos to make this concrete.

AllanMangeni/x402-recovery

This package now includes:

  • a seven-state in-memory settlement state machine
  • connectivity-aware environment profiles
  • a viem-based pollUntilResolved(...) implementation against RPC receipts
  • deterministic tests for success, late confirmation, revert, unresolved RPC errors, and timeout paths
  • a middleware handoff contract via SettlementContext
  • an Express middleware path that reads res.locals.x402Settlement after next() and starts recovery when timedOut === true

Current handoff shape:

interface SettlementContext {
  settlementId: string;
  txHash: `0x${string}`;
  validBefore?: number;
  timedOut: boolean;
}

Current middleware behaviour:

  • downstream handler sets res.locals.x402Settlement when a facilitator timeout occurs
  • middleware checks that context after next() returns
  • when timedOut === true, middleware registers the settlement and starts pollUntilResolved(...) as a fire-and-forget async branch

AllanMangeni/x402-migration-architecture-example

The migration demo has been tightened so Stage 3 now accurately describes itself as:

  • x402-native simulation on Base Sepolia RPC
  • RPC-level latency / settlement simulation
  • a visible extension point toward x402-recovery

That repo is intentionally not presented as a full facilitator implementation. Stage 3 uses synthetic tx IDs for the demo path and documents that limitation directly. Docker and Toxiproxy notes are now aligned with that behaviour.

    The validBefore boundary as natural state expiry is the right primitive.     Happy to share — schema below. Quick orientation: x402trace writes one JSONL file with six event discriminants. The four exchange.* and decoder.error events come from the decoder (documented at src/decoder/schema.md); the two reconciliation-side events come from the chain subscription + reconciliation engine (currently documented as code in src/cli/replay.ts and src/reconciliation/types.ts — I'll fold them into schema.md as part of v0.3 so the doc is one-stop).

    The four-tuple lives in three places. A persistence layer keyed on the canonical (payer, payTo, value, nonce) can match across all three:

    1. exchange.payment — payload.authorization.{from, to, value, nonce}. The payer is from.
    2. chain.transfer — {from, to, value, authorizationNonce}. authorizationNonce is only present when the on-chain Transfer event was enriched with the matching AuthorizationUsed event from the same tx (the chain subscription does this enrichment per ARCHITECTURE.md).
    3. reconcile.result — the join output. Discriminated by kind:
    {
  "event": "reconcile.result",
  "exchangeId": "<uuid>",
  "kind": "settled_on_chain",
  "transfer": {
    "txHash": "0x116ccf73…ba52",
    "from": "0x…",
    "to": "0x…",
    "value": "1000",
    "authorizationNonce": "0xa3f2…",
    "blockNumber": "41402768",
    "blockTimestamp": 1750000000
  },
  "pending": {
    "payer": "0x…",
    "payTo": "0x…",
    "value": "1000",
    "nonce": "0xa3f2…",
    "validBefore": 1750000300
  }
}

    Other kind values: not_settled (watch window exhausted), value_mismatch (on-chain transfer value diverges from authorization), recipient_mismatch (on-chain transfer paid the wrong address). Each maps onto a different failed_orphaned sub-state in your taxonomy.

    bigint convention: anything that's a uint256 on-chain (value, blockNumber, nonce) is serialized as a string in the JSONL so JSON.parse doesn't lose precision. Read back via BigInt(s). The replay loader in src/cli/replay.ts does this round-trip.

    Idempotency: reconcile.result is idempotent on (pending.payer, pending.payTo, pending.value, pending.nonce). The engine emits exactly one result per pending, ever — so persisting that tuple as the primary key + a kind column gives you both dedup and state.

    validBefore as state boundary: the engine drops pending records once Date.now() > validBefore, no separate TTL. The chain transfer can still arrive after that point (and we'd still log it as chain.transfer), but the join is no-op past validBefore because the pending side is gone. A middleware that wants the symmetric guarantee can just stop polling at validBefore + reorg_safety_margin.

    @danielnorkin — your multi-chain observation is useful here. The chain.transfer event is chain-agnostic in shape (just {from, to, value, tokenAddress, ...}); x402trace v0.2 is hard-coded to Base Sepolia, but v0.3 (lands within the next few weeks) adds Base mainnet, and the same shape would extend cleanly to any EVM chain whose USDC honours EIP-3009. Happy to compare notes once that's out.

    Quick update from the x402-recovery side.

    I am narrowing the package scope based on the discussion here. The package should not try to own facilitator-side dedup or become a replacement for upstream settlement verification. The useful gap is more specific:

    facilitator settlement times out or becomes uncertain, but the chain may later confirm success.

    For that reason, I am aligning the next x402-recovery version around these assumptions:

    1. Durable settlement identity should be the 4-tuple:
    canonicalKey(payer, payTo, value, nonce)

    settlementId can remain useful as a local record or job ID, but persistent recovery should key on the canonical payment tuple.

    1. validBefore should be treated as the recovery TTL.

    Once validBefore has passed, the authorization can no longer be spent, so recovery can safely move to an orphaned/archivable state.

    1. Receipt lookup should be abstracted.

    Instead of binding recovery directly to viem, the package should expose a small receipt-provider interface and ship a viem adapter. That leaves room for upstream x402 to standardize receipt verification without making recovery code stale.

    1. Facilitator dedup should live upstream.

    x402-recovery should focus on post-timeout reconciliation and late confirmation, not on replacing facilitator internals.

    The main upstream hook that would make this cleaner is a structured timeout/settlement-observation hook, something like:

    afterSettleTimeout({
  payer,
  payTo,
  value,
  nonce,
  txHash,
  validBefore,
  network,
  facilitatorResponse,
})

    Adding a complementary data point: the Two-Phase Gap framing maps onto the batch-settlement scheme too, with a slightly different shape that the current discussion (focused on the exact scheme + EIP-3009) doesn't cover. Worth mentioning because the unified resolution at the protocol/middleware layer probably needs to handle both.

    In exact (EIP-3009 path), the gap is between the facilitator's timeout clock and chain finality — one transaction in flight. In batch-settlement, the same flow has two transactions in series from the same facilitator-delegated sender — claim then settle(receiver, token) — and the gap surfaces twice:

    1. Between claim mining and settle dispatch — if the facilitator submits settle before the claim tx confirms, both reuse the delegated sender's nonce and the RPC rejects the second one as replacement transaction underpriced. Same shape as the exact timeout race but on the second tx.

    2. Between claim mining and the facilitator's settle view — even after the claim is confirmed on-chain (eth_getTransactionReceipt returns status: "0x1"), the facilitator's settle path reads an indexed view that lags the chain by a few seconds and returns invalid_batch_settlement_evm_nothing_to_settle. This is a third clock — indexer time — that the framing in this issue doesn't currently name.

    Reproducible evidence and the two failure modes are in #2471, with on-chain tx hashes for both. Single-process client-side workarounds shipped in Adelagric/x402-batch-settlement (wait_for_receipt between legs + bounded settle retry) close the loop in one trigger.

    Implication for the middleware design proposed here: the seven-state machine works for batch-settlement too if pending → confirmed is decomposed into claim_pending → claim_confirmed → settle_pending → settle_confirmed, with an explicit allowance for the indexer-lag transition before settle dispatch. The "three clocks" table in your issue is right but likely needs a fourth row: indexer time (facilitator's view-of-chain), which can be longer than block inclusion under load.

    Happy to share more if useful — there's a single-process closed-loop demonstration on Base Sepolia (four consecutive single-trigger settlements, settledAmount matching the on-chain RECIPIENT delta to the raw unit) in the repo above. The implementation is Rust but the shape is scheme-agnostic.

    @cv-scvd Speaking from the batch-settlement side rather than exact, but the shape of the answer carries over: what I shipped in Adelagric/x402-batch-settlement is essentially the lightweight version you're describing — in-memory pending record, bounded retry on a timer, no persistent store — and it closed the loop reliably across the runs in RESULTS.md. So yes, the simplification is real. But it's safe only under three conditions, and it's worth being explicit about which edge case each one absorbs:

    1. Match on the full four-tuple (payer, payTo, value, nonce), never nonce alone. This is what neutralizes the same-nonce-different-authorization case fardinvahdat hit upthread. The danger there was never the polling cadence — it was the matching key. With the canonical tuple as your key, even a single poll can't be fooled into claiming the wrong settlement; with nonce-only matching, no amount of state-machine sophistication saves you.

    2. Time the poll for the facilitator's read lag, not the chain's. One caveat on "poll once, on a timer": in my Base Sepolia runs the facilitator's indexed view lagged a confirmed receipt (status: 0x1) by ~10–15 s median with a tail out to ~45 s. A single poll fired shortly after your timeout can return a false "not settled" while the settlement is sitting in that window. Two cheap reads beat one: an early check for the happy path, plus a terminal check at validBefore (+ a reorg safety margin) as the authoritative answer. Still no state machine — just two timer entries instead of one.

    3. Accept what the missing persistence actually costs: crash-safety, nothing else. The full pending/polling/confirmed_late graph buys you recovery across process restarts. If your seller process dies mid-window, the in-memory pending record dies with it and that payment's ambiguity is never resolved. For low volume, the middle ground is an append-only JSONL line per pending (the x402trace schema upthread is already the right shape), replayed on startup — a file, not a state store.

    Caveat on my data: batch-settlement scheme, n=4 closures on Base Sepolia, so treat the lag numbers as anchors rather than gospel. But the three conditions are scheme-agnostic. For your CDP situation specifically, condition 2 is doing extra work: since CDP doesn't publish what "settled" means per rail, your own terminal check at validBefore against the chain is the only ground truth you get — which is an argument for keeping it even in the most minimal version.

    @postdvk It's live. This is in production in x402-recovery.

    The close-out rule is a state transition, not a retry. Polling runs until the profile maxPollWindow elapses. If RPC is still inconclusive at that point:

    • if validBefore has passed, the record goes failed_orphaned (the authorization can no longer be spent, so it is safe to archive)
    • otherwise it goes failed

    unresolved is the mid-poll escape hatch (aborted poll, unknown receipt, or a non-retryable RPC error), not the terminal "window expired" state.

    The package owns deadline → state. The resource server / operator owns what that state means for the user: withhold delivery, return 402, notify, or send to review. Recovery does not retry the payment or set that policy.

    @infinitybobina — good question, and the honest answer has a correction baked into it.

    We didn't end up shipping the lightweight version Adelagric and I were sketching in the comments above. What shipped three days later (2026-08-28) is a heavier, fully durable state machine — and reading its own code comments now rather than my memory of the timeline, it wasn't built because of this thread. The documented reason is a separate, earlier incident: 2026-08-07, a buyer told "no" three times by us, paid three times anyway, discovered ten hours later by hand reconciliation. Worth being straight about that — this conversation didn't change our build plan, it just landed two days before something already queued.

    What actually shipped (verified against commit a7528575ebbb3fd5eb2de8d6b65572f86f33cd4c, src/services/settlement-unknown.ts): every settle attempt that ends with no verdict (threw mid-flight, or both the inline attempt and the inline chain rescue failed — wrong rail, or RPC down too) writes a durable KV row in open state, 90-day TTL, instead of living in process memory. An hourly cron pass (resolveSettlementUnknowns, bounded to 8 rows and 4 chain-read chunks per row per pass) re-asks the chain directly: scans a block-estimated window for the EIP-3009 AuthorizationUsed(payer, nonce) event, bounded on the far edge by the authorization's own validBefore (the contract enforces that at execution, so a nonce not burned by then never can be). Three outcomes: settled_late (found on-chain — money moved, goods didn't; this opens an admin alert plus a delivery-intent row, the same desk any other undelivered sale gets worked by hand) and expired_unused (window fully covered, authorization's own clock ran out, original decline stands). If the chain can't be read, the row just stays open and ages out at 7 days to aged_out_unresolved — explicitly "we couldn't answer," never "no," backstopped by a separate monthly reconciliation pass.

    Against your two conditions specifically: we match on (payer, nonce) rather than the full four-tuple, which is safe for us only because AuthorizationUsed is itself keyed by authorizer+nonce and the contract enforces nonce-uniqueness per authorizer — there's no same-nonce-different-terms case at that layer to collide on. And we never had your facilitator-read-lag problem to time around, because this doesn't poll the facilitator at all — it reads the chain directly, so there's no indexer lag window to sit inside of.

    What I can't give you cleanly: an aggregate count of how many rows have actually landed in each state since launch — I didn't pull that number for this comment and don't want to guess at it. What I can say verified: the ambiguity itself has been mechanical since 08-28, not hand-reconciled. Whether a resolved settled_late row then needs a human — it does, by design, someone still decides refund vs. fulfill — is a separate question from whether we had to resolve the ambiguity by hand, and the answer to that one is no, not since this shipped.
