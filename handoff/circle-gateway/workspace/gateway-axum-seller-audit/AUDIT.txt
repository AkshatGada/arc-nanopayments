1. [P2] Redirects bypass the configured facilitator origin restriction

Location: gateway-axum-seller/src/lib.rs:57-58
Related guard: gateway-axum-seller/src/config.rs:81-92

Config validates the initial facilitator URL, but the pinned upstream
FacilitatorClient constructs Reqwest's default Client, which follows redirects.
A 307 from POST /v1/x402/settle can replay the full original paymentPayload,
including its authorization/signature fields, to another origin. A correctly
shaped receipt from that destination is then accepted by the seller.

Reproduction: the configured loopback mock redirects to a second server on
another loopback port. The second origin receives the original paymentPayload,
returns the synthetic accepted receipt, and /quote returns 200.
Observed: redirected quote status = 200 OK, captured settlements = 1.

Condition/limit: the configured endpoint must issue a redirect. This is not
evidence that an arbitrary buyer can choose a redirect destination, nor that
Circle currently redirects payments. No real signature or payment was used.

Suggested correction: disable redirects for Gateway discovery/settlement, or
enforce the configured origin and secure scheme on every redirect hop. The
upstream client currently exposes no injected HTTP client/redirect policy, so
this needs a transport API adjustment or a strict local Gateway transport.
Add negative 307/308 cases asserting zero destination calls and no fulfillment.

2. [P2] HTTP error responses can still release paid content

Location: gateway-axum-seller/src/lib.rs:155-157
Dependency: pinned x402-axum src/facilitator_client.rs:399-405

The generic upstream client deserializes HTTP 200, 400 and 412 into the same
settlement wrapper, discarding the status. GatewayFacilitator then accepts a
body with success:true and the expected payer/network/UUID. Consequently an
HTTP error status with a success-shaped body still runs the handler and returns
200 with an acceptance receipt. The current tests cover HTTP 500 success-shaped
bodies but miss 400 and 412.

Observed independently for each response:
  upstream=400 Bad Request seller=200 OK fulfilled=1
  upstream=412 Precondition Failed seller=200 OK fulfilled=1

Condition/limit: the trusted endpoint must produce an inconsistent error-status
and success-body response. This is a confirmed failure to reject contradictory
upstream results, not an unauthenticated buyer payment bypass against Circle.

Suggested correction: require HTTP 200 for successful Gateway acceptance
before interpreting the receipt, preserving status metadata through transport.
Add 400/412 success-shaped-body tests expecting no handler execution and a
redacted failure response without a fresh payment offer.
