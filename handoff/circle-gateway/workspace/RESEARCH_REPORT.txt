Circle Gateway / Nanopayments contribution research
Research date: 16 October 2026 (Asia/Kolkata)
Scope: public-source research and synthetic offline probes only.

RECOMMENDATION

Start with a native Rust/Axum Gateway seller example and a small compatibility
suite using the existing x402-rs crates. A new Rust seller SDK is not justified
by the code inspected: the existing generic middleware can advertise Gateway
requirements and call Circle's hosted settlement API directly. The research
probe demonstrates this without modifying upstream code.

The deeper follow-up is explicit Rust buyer discrimination/support for Gateway.
Do not present this as changing the generic onchain EIP-3009 facilitator to use
a different contract. Upstream has already considered and closed that approach.

Keep the career proof concrete: an interoperable Rust seller, a reproducible
buyer incompatibility, and tests distinguishing accepted payments from final
onchain settlement. This is evidence for a technical conversation, not a claim
of Circle endorsement, a production launch, or an accepted contribution.

PAYMENT MECHANISM AND SETTLEMENT BOUNDARIES

Gateway Nanopayments: deposit USDC into GatewayWallet; sign independent
TransferWithAuthorization messages using the GatewayWalletBatched EIP-712
domain; submit through Circle; Circle admits/locks payment and later settles
net balance deltas in a signed batch. Its signing contract differs from the
USDC asset address. This is not a cumulative payment channel.

The API's verify response is read-only validation. The OpenAPI specification
says balance and nonce checks occur at settle time, so verify success alone
does not guarantee payment. Circle's integration docs recommend calling settle
directly for production Gateway flows. A successful settle response contains
a transfer UUID in transaction, not a batch transaction hash.

Transfer states are received, batched, confirmed, completed and failed. A
separate nullable txHash identifies the batch-level onchain transaction. The
existing reconciliation guide distinguishes acceptance from settlement and
uses nonce lookup, transfer ID lookup, recipient/date filters and pagination.
There is already a public API for this; do not propose it as missing.
https://developers.circle.com/openapi/gateway-nanopayments.yaml
https://developers.circle.com/gateway-nanopayments/howtos/x402-seller-reconciliation
https://developers.circle.com/gateway-nanopayments/concepts/batched-settlement

The reconciliation guide's own example still stores ctx.result.transaction as
txHash and timestamps the acceptance hook as settledAt. A narrow correction
to transferId/acceptedAt, followed by actual status/txHash observation, would
align the code with the guide's prose. This is a confirmed example mismatch;
it is not proof of a hosted accounting defect.

AXP comparison: Akshat explicitly reports that AXP uses BOTH Solana and Tempo
payment channels. No AXP source was inspected in this assignment. The relevant
shared idea is amortizing onchain work across many offchain authorizations.
Reference channel mechanisms use funded channel state and cumulative vouchers,
with claims/settlement/refunds or close procedures. Gateway instead nets
independent authorizations via Circle's hosted ledger/enclave infrastructure.
Do not transfer claims about AXP's exact voucher, recovery, custody, finality or
performance properties from these reference implementations.
https://solana.com/news/payment-channels-1-million-payments-per-second
https://mpp.dev/blog/sessions-improved
https://github.com/x402-foundation/x402/blob/main/specs/schemes/batch-settlement/scheme_batch_settlement_evm.md

RANKED CONTRIBUTIONS

1. Native Rust/Axum seller example plus Gateway compatibility fixtures.
   Best initial Circle-specific proof; narrow scope and verified feasibility.
   Use existing x402-axum and a generic v2 PriceTag preserving the entire
   Gateway extra object. Configure the Circle /v1/x402/ base correctly and use
   settle_before_execution. A generic facilitator URL alone is insufficient:
   the seller must advertise Gateway metadata and use the right order.
   Deliver one runnable seller, environment-driven receive address/network,
   bounded integer pricing, startup supported-kind validation, a correct
   transfer-ID receipt, EOA/network limitations and offline failure fixtures.
   Include unpaid 402, accepted payment, rejected settlement, mismatched terms,
   malformed payload, timeouts and acceptance-vs-confirmation cases. No local
   signer, deposit/withdraw implementation or new SDK is needed for the seller.
   Candidate home: x402-rs examples with a Circle skill/reference follow-up;
   actual upstream destination/acceptance remains a maintainer decision.
   No matching native Rust Gateway seller PR was identified in the inspected
   Rust PR list, Circle repos or targeted public searches. This is a scoped
   search result, not proof nobody is working on it privately.

2. Explicit Rust buyer Gateway selection guard / optional Gateway adapter.
   Stronger library-level engineering follow-up, requiring design alignment.
   Offline probe confirms V2Eip155ExactClient accepts GatewayWalletBatched as
   a candidate yet requests a digest using USDC as verifyingContract. It
   preserves the accepted metadata, so metadata loss is not the problem.
   First bounded deliverable: explicit unsupported-Gateway rejection or
   separate Gateway scheme routing with regression fixtures. A full adapter
   should pin/validate network-domain-contract combinations and authorization
   validity policy and use Circle's hosted settlement route. Avoid generic
   trust of a seller-provided verifyingContract. Do not change standard x402
   onchain settlement to call GatewayWallet.transferWithAuthorization.
   Crucial existing work: x402-foundation PRs #2885, #3174, #3175 and #3176
   were closed after this incorrect generic-facilitator premise was rejected.
   The Rust mismatch is confirmed incompatibility, not a newly discovered
   exploitable flaw or proof that generic exact must implement Gateway.
   https://github.com/x402-foundation/x402/pull/3174
   https://github.com/x402-foundation/x402/pull/3175
   https://github.com/x402-foundation/x402/pull/2885

3. Acceptance-to-settlement reconciliation example, not a new reconciliation API.
   Good Circle-focused second contribution if app owners want it.
   Use the existing transfer UUID/nonce APIs to demonstrate accepted, batched,
   confirmed, completed, failed and unknown states. Keep transferId separate
   from batchTxHash; store nonce/network/asset/payer/payee/amount and a durable
   application correlation ID. Use a restartable paginated read-only worker
   with fixtures for null txHash, repeated pages, absent attribution, mismatch,
   delayed settlement and transient API errors. Never infer confirmed from
   the HTTP response or simply total local payment rows as withdrawable cash.
   The current app stores settleResult but no authorization nonce, so transfer
   ID lookup is available, while robust nonce recovery requires a capture
   change. PR #42 substantially rewrites this app: align rather than fork it.
   Existing third-party explorers/ledgers mean a broad dashboard would overlap.
   https://github.com/the-canteen-dev/circle-agent
   https://github.com/broccolirob/ledgerline

4. Small Rust client feature-build fix with a feature-matrix regression check.
   Confirmed offline: x402-chain-eip155 with only feature client fails with
   unresolved tracing in v2_eip155_upto/client.rs at lines 288 and 393, because
   tracing is optional under telemetry. client+telemetry compiles and runs the
   buyer probe. This is a genuinely bounded first upstream code fix, but its
   career signal is lower and it is not Circle-specific. No matching fix was
   found in the complete 82-PR Rust list inspected. No patch was implemented.

5. Narrow documentation/contract fixtures for authorization validity and receipts.
   SDK 3.5.0 constants publish a 7-day minimum plus a 100-second buffer; manual
   signing docs say at least 3 days; the old sample advertises 4 days. Existing
   sample PRs #23 and #33 already address validity issues, and #42 upgrades
   SDK dependencies. First establish the intended hosted contract with Circle;
   do not independently assert which minimum is live. Deliver one consistent
   policy and matching fixtures/docs, not another duplicate sample PR.

EXISTING WORK THAT SHOULD CHANGE THE PLAN

- circlefin/arc-nanopayments #43 already reports logical-purchase retry safety;
  #44 and #47 are open implementations. #44 explicitly acknowledges a concurrent
  check-before-settle race. Its replay branch also re-executes the handler,
  rather than recovering an exact cached application result. #47's key function
  hashes payer+endpoint without the Idempotency-Key value and stores state only
  in memory. These are code-review findings, not live exploit tests. A useful
  contribution is a race/crash/request-binding test proposal for the existing
  work, not a third competing idempotency implementation.
